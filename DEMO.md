# OrgLens AI — показ готового результата Astra за 2–3 минуты

Основной показ использует результат **реального семантического запуска Astra, выполненного заранее**. На сцене показываем уже полученный ответ, не обещаем новый анализ за несколько секунд. Проверенные полные запуски занимали примерно 90–101 секунду; это наблюдение, а не гарантия скорости. Frontend ждёт до 150 секунд, обращение backend к OpenAI ограничено 120 секундами без автоматических повторов. Проверки зафиксированы в [checkpoint 2](docs/CHECKPOINT2.md).

## Подготовить до выступления

1. Запустить подготовленный frontend и настроенный backend в режиме `semantic` по [README](README.md). В frontend должен быть доступен настоящий API: `VITE_USE_MOCK=false` либо переменная отсутствует. Секреты остаются на backend; их не показывают на экране.
2. Выбрать два разрешённых для показа DOCX, нажать «Анализировать изменения» и дождаться полного ответа заранее. Проверить `LIVE ANALYSIS`, «Семантический анализ», имена документов и `analysis_id`. Надпись `semantic` показывает режим; сама по себе она не подтверждает название модели. Для утверждения «Astra» используйте проверенный запуск с соответствующей конфигурацией CORE.
3. Выбрать в этом результате одно понятное преобразование, одно сопоставление функции и один вывод `NEEDS_REVIEW` с читаемыми исходными фрагментами. Не привязывать выступление к фиксированному числу находок. Проверить «Аналитическую оценку сервиса» и её источники, если она получена.
4. Открыть «Заключение» → «Сформировать заключение» → «Скачать заключение». Заранее настроить запрос места сохранения в браузере и сохранить Markdown в `artifacts/prepared-semantic/` внутри репозитория. Там же сохранить скриншоты обзора, оснований и заключения с пометкой «Заранее выполненный semantic-анализ», `analysis_id` и временем подготовки. Это ignored-материалы; документы, цитаты и отчёты не коммитить.
5. Вернуться в «Обзор изменений» и **оставить эту вкладку открытой**. Не обновлять её, не нажимать «Сбросить демо», не запускать новый анализ и не пересобирать frontend перед показом. Результат хранится в памяти вкладки: persistence и импорт сохранённого JSON в UI не реализованы. Дублирование URL не переносит результат.
6. Подготовить отдельные резервные материалы по [DEMO_BACKUP.md](DEMO_BACKUP.md): deterministic-анализ через backend без LLM и автономный синтетический `DEMO DATA`.

## Сценарий — 2 минуты 40 секунд

| Время | Действие | Что сказать |
| --- | --- | --- |
| 0:00–0:20 | Открытый «Обзор изменений»: показать `LIVE ANALYSIS`, «Семантический анализ», документы и ID. | «Это результат настоящего запуска Astra на выбранной паре документов. Мы выполнили анализ заранее: он занимает около полутора минут. Сейчас покажем готовый результат и как его проверить». |
| 0:20–0:45 | Показать сводку и граф. Открыть подготовленное преобразование, затем закрыть основания клавишей Escape. | «На карте видно изменение структуры. Числа относятся к этому запуску. У преобразования есть объяснение, статус и исходные пункты». |
| 0:45–1:10 | «Сравнение функций» → подготовленная строка → основания. | «Сопоставляем ответственность и владельцев. Здесь точные фрагменты до и после. Процент — оценка сопоставления, а не измеренная точность продукта». |
| 1:10–1:45 | «Риски и выводы» → выбранный вывод `NEEDS_REVIEW`. Показать цитату и объяснение отдельно. | «Источник и интерпретация — разные части результата. Цитата взята из документа; гипотезу о переносе, потере, дублировании или конфликте проверяет специалист. Поэтому статус остаётся “Требует проверки”». |
| 1:45–2:10 | «Заключение»: показать «Аналитическую оценку сервиса», статус и источники, если блок есть. | «Astra вернула аналитическую оценку. Её основания доступны рядом, а статус проверки сохраняется. Интерфейс оформляет полученные данные и не запускает модель повторно при формировании отчёта». |
| 2:10–2:30 | Показать «Скачать заключение», покрытие источниками и ограничения. При необходимости вернуться к «Действиям сервиса». | «Markdown сохраняет выводы, рекомендации и основания. Покрытие цитатами не равно подтверждённости выводов. Журнал действий пришёл вместе с завершённым ответом; это не поток рассуждений». |
| 2:30–2:40 | Завершить на заключении. | «OrgLens помогает эксперту увидеть изменения и проверить каждое существенное наблюдение по исходному документу». |

Перед переходом в другой раздел закрывать панель оснований клавишей Escape. Если в выбранном ответе нет аналитической записки или подходящего вывода, показать фактическое состояние без обещания отсутствующего блока. Для сокращения до двух минут пропустить журнал действий и уменьшить время на графе. Для трёх минут подробнее сверить одну цитату.

## Как обозначать источник показа

- Открытый результат: «Заранее выполненный реальный semantic-анализ Astra». `LIVE ANALYSIS` обозначает происхождение ответа из API, не момент его получения.
- Сохранённый Markdown или скриншот: «Заранее подготовленный материал того же запуска», с `analysis_id`. Не представлять его как новый live-ответ.
- Deterministic fallback: «Настоящая обработка DOCX backend без языковой модели»; в UI остаётся `LIVE ANALYSIS`, режим — «Детерминированный анализ».
- Offline fallback: «Локальный синтетический пример»; метка — `DEMO DATA`, данные и этапы подготовлены заранее.

Не обещать постоянное число находок, фиксированное время или измеренную точность. Не считать точность цитаты доказательством интерпретации. Ответы на вопросы — [JUDGES_QA.md](JUDGES_QA.md).
